# Contributing to Ostia

Conventions for people and coding agents (Claude Code, Codex) working in this repo. Claude Code users: add `@CONTRIBUTING.md` to your local `CLAUDE.md` (it is not tracked) so your agent reads this file. Codex reads it through `AGENTS.md`.

## Workflow

1. **Open an issue first.** One problem per issue, in English: what is wrong, what is expected, and a "Done when" line. Label it (see below) and set the milestone.
2. **Branch from the latest `main`**: `<type>/<short-description>`, where type is `fix`, `feat`, `docs`, `refactor`, `test` or `ci`. `main` is protected: every change, admins included, goes through a pull request, and force pushes and branch deletion are blocked.
3. **Commit** with [Conventional Commits](https://www.conventionalcommits.org/) in English (`fix(terminal): …`, `feat(browser): …`). No comments in code, YAML (workflows, actions, config), shell scripts or other config; shebangs and tool directives stay. `scripts/comments.mjs` rejects them in code, and nothing checks the rest, so review it.
4. **Check before pushing**:
    - `pnpm typecheck`, `pnpm lint` and `pnpm exec vitest related <changed files> --run`. CI runs on every PR the unit tests and Linux e2e specs your diff affects (see CI below), every unit test and the `@core` e2e tests in the merge queue, and every Linux e2e spec (release candidates skip `@experimental`) plus the macOS groups on release candidates and every night.
    - when a change needs e2e evidence, run only the specs you touched on CI: `gh workflow run ci.yml --ref <branch> -f full=true -f specs=e2e/<spec>.ts` (see CI below)
    - macOS-only behaviour (menus, Cmd keys) on a real Mac. For a bug fix, revert only the code, keep the new test, and confirm the test fails.
    - scan the whole branch for secrets (tokens, keys, certificates); nothing may match
5. **Open a PR.** First line of the description: `Closes #N` (one line per issue). Then why, what changed, how it was tested, and what is not verified yet. Same labels and milestone as the issue. Check the link with `gh pr view <N> --json closingIssuesReferences`.
6. **Merge** only when CI is green and a maintainer says so, by adding the PR to the merge queue. Agents never merge or approve on their own. Use a merge commit (no squash) and delete the branch. If two PRs conflict, the author of the later one merges `main` into their branch; no force pushes.
7. **Release**: bump `package.json` in a pull request, then tag `v*` on `main` (a `-rc.N` tag cuts a pre-release). The tag runs the full CI, e2e included, and the macOS signing job waits for a maintainer to approve the `release-macos` environment.

## Supported platforms

macOS and Arch-based Linux (CachyOS) come first. Debian and Ubuntu are supported too, but a bug there ranks below the same bug on those two.

## Labels

The labels (name, colour, description) are defined in `.github/labels.yml`; change that file and the repository labels together.

Every issue and PR gets **one `type:`**, **one or two `area:`**, a **`platform:`** only when it is platform-specific, and (issues only) **one priority**.

- `type:` `bug`, `feature`, `enhancement`, `docs`, `refactor`, `test`, `ci`
- `area:` `terminal`, `agents`, `extensions`, `sandbox`, `settings`, `keybindings`, `ui`, `browser`, `editor`, `remote`, `cli`, `release`
- `platform:` `macOS`, `Linux` (Windows is not supported; use `wontfix`)
- Priority: `P0` crash, data loss or security · `P1` blocks daily use · `P2` normal · `P3` nice to have
- `status: needs triage`, `status: needs decision`, `status: blocked` when they apply; progress is shown by linked PRs, not labels
- `agent: ready`: the issue has a clear spec and "Done when", so an agent can pick it up as is

## Milestones

One milestone per minor version, named `v<major>.<minor>: <theme>` in English, e.g. `v0.5: Stable daily driver`. Patch releases (0.5.7, 0.5.8) stay under their minor's milestone; releases themselves are git tags and GitHub Releases. A milestone whose theme is not decided yet is called `Next milestone`.

Every issue and PR gets the milestone of the release line it lands in. Open milestones: `v0.5: Stable daily driver` (current release line), `v0.6: Bug fixes`, `v0.7: Next milestone`.

## CI

- Pull requests and pushes to `main` run static checks, Linux unit tests and builds (a push to `main` the merge queue already passed skips them, see below); the macOS unit tests (`unit-macos`) run on pushes to `main`, tags, the nightly run and manual runs, not on pull requests. A pull request runs only the tests its diff against the merge-base can affect (`scripts/affectedTests.mjs`, rules in `test/affectedTests.mjs`). Unit: `vitest related` over the changed files, every node test once a change reaches code outside `src/renderer` (the CLI, extensions and SDK built for the tests bundle it), and the tests that read files at run time: dom tests that import `fs` (for a `src/` change), and node tests that import `fs` and name `e2e` or `.github/` (for a change there). A change to `test/quarantine.json` runs `test/quarantine.test.ts` and the tests whose entries changed; a change to `.github/` alone runs only the tests that read it. Any other change outside `src/`, `e2e/` and `.github/` (lockfile, `package.json`, configs, `test/`, `scripts/`), other than a root `*.md`, runs every unit test. e2e (Linux): the specs the PR changed, the specs importing a changed file, the specs of every area in `test/e2eAreas.json` whose paths a change starts with, and the `@core` tests, by file and line, for a code change no area or import claims (hub files such as `src/main/app.ts` or `src/shared/app/dict.ts` are left out of every area on purpose). Docs, unit tests, `.github/`, `test/` tooling and unit-only configs run no e2e. Up to 20 specs run in one job (five `@core` tests count as one spec), and every 20 more add a shard, up to four (`e2eShards` and `e2eWeight` in `test/affectedTests.mjs`); a full pull request run and a manual run on a branch use four. A change to the e2e harness (`e2e/helpers.ts`, `e2e/dataHome.ts`, `e2e/test.ts`, `playwright.config.ts`, `scripts/e2e.sh`), or a plan that fails, runs the full Linux suite. A new spec without a `@core` test goes into an area of `test/e2eAreas.json` (`test/e2eAreas.test.ts` fails otherwise, and also on a spec or path that no longer exists). The merge queue, pushes to `main`, the nightly run and tags run every unit test, and the queue the `@core` e2e tests, so a broken core flow is caught before it lands; anything else the PR plan missed shows up in the nightly run. `@core` marks the user flows that gate the merge queue (launch, type, split, close a pane, restore, start a worker, send and read back, shortcuts, clipboard, settings, quit), at most 34 tests (`test/e2eImports.test.ts`). The e2e suites (every Linux spec in six shards, and the macOS groups) run for `v*` tags and every night on `main`, and on demand in four Linux shards: `gh workflow run ci.yml --ref <branch> -f full=true`, or Actions → CI → Run workflow; a manual run on a tag ref runs the e2e suites like a tag. Tags skip `@experimental` tests; the nightly run keeps them. Every night `e2e-race` runs the `@race` tests ten times (`--repeat-each=10`), and every night and on tags `e2e-macos-core` runs the `@core` tests on macOS; neither blocks `ci-result`. The merge queue runs the `@core` tests in two Linux e2e shards (GitHub-hosted, no `e2e-ptrace`, no macOS) for a group that changes code, and blocks the merge on them.
- A manual run can be narrowed with three inputs. `platform` is `all` (default), `linux` or `macos`: `linux` starts no macOS job, `macos` starts no Linux e2e job (static, unit and build still run on Linux). `specs` is a space-separated list of e2e files or patterns; when set, Linux runs one e2e job instead of the shards and macOS runs one job instead of the five groups. `repeat` is passed to Playwright as `--repeat-each`. The inputs only apply when `full` is true. Examples:
    - `gh workflow run ci.yml --ref <branch> -f platform=linux -f specs=e2e/system.spec.ts -f repeat=3`
    - `gh workflow run ci.yml --ref <branch> -f platform=macos -f specs="e2e/ssh.spec.ts e2e/ssh-remote-files.spec.ts"`
- `changes` and `unit` always run on GitHub-hosted `ubuntu-24.04` (unit needs sudo for apt and an AppArmor sysctl). For maintainer pushes and PRs, the Linux jobs run on self-hosted ARC runners on Kubernetes, sized per job: `static`, `unit-dom`, `build` and the Linux e2e shards on `ostia-linux` (4 CPU / 8 Gi), and `ci-result` and `e2e-report`, which do seconds of work, on `ostia-linux-small` (2 CPU / 4 Gi). `unit-macos` runs on a self-hosted Mac. Fork PRs run on GitHub-hosted runners only, and so do `v*` tag runs (every Linux job, `ci-result` and `e2e-report` included, plus `package` and publish), like nightly and the merge queue.
- Pull requests merge through the merge queue once the fast checks are green (static, Linux unit, build, `ci-result`). The queue merges `main` with the queued pull requests ahead of it and runs the same jobs on that commit (`merge_group`, on GitHub-hosted runners, without `unit-macos` and `quarantine`) with every Linux unit and dom test, not only the affected ones, and for a group that changes code also runs the `@core` e2e tests in two Linux shards (GitHub-hosted, no `e2e-ptrace`, no macOS) and blocks the merge on them, so two pull requests that pass alone but break `main` together, or break a core flow, are caught before they land. A docs-only group skips every job but `changes` and `ci-result`. A code group in the queue waits for the two `@core` shards. Pushes to `main` run one at a time: a push that arrives while one is running waits, and a newer push replaces the waiting one. `unit-macos` does not run on a PR, and Linux e2e blocks a PR only through the queue; macOS e2e and `unit-macos` run in full on `-rc.N` tags and nightly, `e2e-macos-core` runs with them, and `unit-macos` also runs on pushes to `main`. On a `v*` tag `build-macos` and `e2e-macos` must pass for `ci-result` to pass (also when `workflow_dispatch` runs on a tag ref, so a tag can be re-verified); `unit-macos` and `e2e-macos-core` never block. `quarantine` does not run on pull requests or in the queue: it runs 10 times on Linux and macOS in the nightly and manual runs (Linux only when a manual run sets `platform` to `linux`), and 5 times on Linux only on pushes to `main` and tags.
- A push to `main` whose commit already passed `ci-result` in the merge queue runs only `unit-macos` and `quarantine`: the merge group's head is the commit that lands, so `static`, `unit`, `unit-dom` and `build` would check the same tree with the same jobs again, and `ci-result` then requires those four to be skipped. `scripts/mergeQueueVerified.mjs` decides this from the GitHub API, never from the commit message: a successful `ci-result` check run by `github-actions` on that exact sha, in a `merge_group` run of `ci.yml` on `gh-readonly-queue/main/*`. It fails safe: no token, an HTTP error, a timeout (15 s per call), an unexpected response or a push that bypassed the queue gives `verified=false`, and the push runs every job as before. The `changes` job summary shows the result and the reason.
- Ask Justin before changing `.github/workflows/ci.yml`, `.github/workflows/release.yml` or `.github/actions/setup/action.yml`; the self-hosted runners depend on them.
- Every job has `timeout-minutes` (about 3× its measured time, at least 10 minutes for a job that downloads packages), and the setup action and test steps have step timeouts. A new job gets one too.
- The Linux jobs get their system packages from `.github/actions/linux-deps` (`packages.txt`): on a GitHub-hosted runner the `.deb` files are cached per image version and package list and installed with `dpkg`, so only a cold cache runs `apt-get`; a self-hosted runner runs no `apt-get`: its image (`ci/images/arc-runner` in homelab-infra) carries every package. Every `apt-get` and the setup action's `pnpm install` run through `scripts/retry.sh` (4 attempts, 10/20/40 s back-off, and each attempt is ended after `RETRY_TIMEOUT` seconds, 300 by default, so a hang counts as a failed attempt instead of running to the job timeout). Never retry tests: a flaky test goes into `test/quarantine.json`. Each entry has an open issue and a date at most 30 days out, or 7 days for a `@core` test (the file's source decides, a tag on its `describe` counts): a `@core` entry needs a maintainer's OK and, in the same pull request, a stand-in test (another `@core` test, or one added at a lower level that reproduces the failure); it may be renewed only while the fix or the stand-in is still in progress. The test keeps its `@core` tag while it is quarantined, so the 7-day limit holds; drop the tag only once a stand-in covers the same flow at the same level or higher. A pull request checks only the entry's format; once the date passes or the issue is closed, `quarantine-dates` fails pushes to `main`, the nightly run and tags, and a week before the date the nightly `Quarantine reminders` workflow comments on the issue once.
- Building node-pty downloads no headers on a warm runner. `pnpm install` compiles it for Node against the headers of the Node that `setup-node` installed (`npm_config_nodedir`, set by the setup action), not a tarball from nodejs.org. `pnpm rebuild` compiles it for Electron from the job's own `~/.electron-gyp`: on a self-hosted runner the setup action copies Electron's headers there from `/opt/ci-cache/electron-gyp/<version>`, and when that version is missing it downloads them (with `scripts/retry.sh`) and publishes them with `scripts/electron-headers.sh`, which copies to a temporary name and renames it into place, so jobs running at the same time never share a writable folder or see a partial copy.
- Tests that need ptrace or `process_vm_readv` fail on the self-hosted Linux runners. Run them on GitHub-hosted Ubuntu, like `PTRACE_E2E` in `ci.yml`.
- Repo variables `OSTIA_SELF_HOSTED_LINUX` and `OSTIA_SELF_HOSTED_MACOS` set to `off` send those jobs back to GitHub-hosted runners (`ubuntu-24.04`, `macos-26`). Changing them needs a maintainer. Only `OSTIA_SELF_HOSTED_MACOS` is set to `off` today, so macOS jobs run on GitHub-hosted runners.
